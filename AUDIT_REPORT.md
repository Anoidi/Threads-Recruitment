# Аудит Threads Recruitment Manager — 2026-10-13

## Объём и доказательная база

Аудит выполнен по фактическому коду, live HTTP API и работающим контейнерам. Код и рабочие данные не изменялись. `docker compose ps`: 8 сервисов healthy/up (backend, worker, frontend, MySQL, Redis, LiteLLM, Hermes, Adminer). `GET /api/health` возвращает `ONLINE/live`; это означает здоровье локального стека, а не полноту внешних возможностей Threads.

Проверено: 96 backend-тестов — `96 passed`; миграции Alembic 0001–0008; frontend/API; worker; модели и очередь; live `/api/threads/account` и `/api/threads/analytics`.

## Пять главных недостатков

1. **Нет измеримого рекрутингового результата.** Live analytics: 15 опубликованных постов, 15 с метриками, 0 candidate signals, 0 кандидатов, 0 подтверждённых контактов и наймов. `coverage.public_threads=unavailable`, причина — нет `threads_keyword_search`. Влияние: невозможно доказать, что контент приводит квалифицированных кандидатов. Действие: ввести воронку `intent → reviewed signal → confirmed contact → qualified → hired`, обязательные статусы, источники и дату подтверждения.

2. **Недостаточно данных для выводов.** В `/api/threads/analytics` только 5 сопоставимых записей; editorial analysis разбивает их на группы по одному посту и возвращает `insufficient_data=true`. Три поста — лишь гипотеза, а не причинность. Действие: хранить снимки 24/48/168 часов, сравнивать когорты минимум 3×2 поста при одной изменяемой характеристике.

3. **Публикация live возможна при слабой операционной защите.** `.env` содержит `THREADS_MOCK_MODE=false`, `AI_MOCK_MODE=false`, а ключ провайдера Threads в окружении пуст; live account при этом уже подключён через зашифрованный токен БД и имеет только `threads_basic`/`threads_content_publish`. Автопост выключен, но ручная публикация доступна. Действие: перед каждой публикацией требовать свежий account readiness, scope check, idempotency reconciliation и явный операторский audit event; разделить health `local-online` и `external-ready`.

4. **Качество украинского и сохранение условий вакансии не гарантированы.** Реальные top posts содержат смешение языков (`Напишите нам` в украинском тексте), некорректные/двойные единицы (`23 зл/год PLN`), странный перевод (`Умова залогу`) и источник новостей, вставленный в тело поста как `[google-news-rss] ...`. Действие: блокировать публикацию при нарушении языка, валюты, обязательных фактов и наличии служебных маркеров; проверять текст по структурированным vacancy facts.

5. **Атрибуция пока заканчивается на сигнале.** Модели связывают interaction → post и signal → candidate, но нет сущностей подтверждённого контакта, consent, канала контакта, recruiter outcome или hiring result. Интерфейс кнопкой «Создать кандидата» превращает сигнал в карточку, что не является подтверждением квалификации. Действие: добавить отдельную сущность conversion/evidence и запретить KPI-карточки до ручного подтверждения.

## Подтверждённые баги и риски

- В live опубликованных примерах присутствуют языковые/фактические дефекты, перечисленные выше; это наблюдаемый результат API, не предположение.
- `public_threads` фактически недоступен: account permissions не содержит `threads_keyword_search`; UI должен показывать unavailable, а не пустой список как нулевой тренд.
- В `.env` обнаружен заданный Telegram Bot token. Секрет в отчёт не выводится. Его нужно немедленно отозвать через BotFather и заменить; наличие `.gitignore` не исправляет уже скомпрометированный токен.
- Метрики API адаптера ограничены `views,likes,replies,reposts,quotes`; shares, link clicks, saves, DMs и переходы не собираются. Их нельзя отображать как нули.
- Аналитический код использует последний snapshot и возрастной bucket; 24/48/168-часовые окна не являются фиксированными измерениями. Это делает сравнение публикаций с разным временем замера слабее, чем требуется бизнес-целью.
- `ThreadsInteraction.post_id` и `remote_parent_id` предусмотрены, а ответы проходят через `/media/{id}/replies`; это хорошая база, но фактическая coverage не доказывает, что весь discussion tree и внешние ответы доставлены API.
- Автотесты подтверждают контракт и mock/live ошибки, но не доказывают реальные Meta scopes, rate-limit quotas, token expiry, restart recovery с live provider или качество украинского на продакционных данных.

## Что уже работает

Вакансия → draft → review → approve → schedule → durable background job → publish: реализованы модели состояний, версии, idempotency keys и уникальность remote/idempotency. Redis используется для wakeup/locks, MySQL — источник истины. Worker имеет retries и recovery для зависших jobs. Live Threads adapter делает двухшаговую публикацию container/status/publish, не повторяет неоднозначный publish POST и классифицирует ошибки.

Community sync, candidate signals, ручная конвертация в candidate, approval reply, metric snapshots, Telegram import и source-linked topic drafts реализованы частично. В mock mode это демонстрационный контур, не подтверждение внешнего результата.

## Автономный цикл и критерии приёмки

1. **Сбор:** posts, interactions, replies tree, metrics snapshots, vacancy facts, source URLs. Приёмка: каждый факт имеет source, fetched_at, API status; unavailable не превращается в 0.
2. **Проверка:** dedupe, scope/capability check, token status, language/fact validation. Приёмка: ни один draft с placeholder/source marker/unsupported claim не проходит в approval.
3. **Анализ:** программные rates и cohorts для 24/48/168h. Приёмка: отчёт показывает denominator, sample size, missing metrics и `insufficient_data`.
4. **Гипотеза:** ровно одна изменяемая характеристика, primary KPI, окно, stop rule. Приёмка: LLM только объясняет вычисленный результат и ссылается на post IDs/snapshots.
5. **Варианты:** 2–3 drafts с сохранёнными vacancy facts и языком uk по умолчанию. Приёмка: human review видит diff и источники.
6. **Одобрение/публикация:** публикация только после отдельного разрешения владельца; destructive/external actions не запускаются агентом. Приёмка: audit event, idempotency key, reconciliation при unknown outcome.
7. **Воронка:** signal ≠ candidate; candidate ≠ qualified; qualified ≠ hired. Приёмка: ручное подтверждение каждого перехода и связь с исходным post/interaction.

## Antigravity CLI и «бесплатное» использование

Официальная документация Antigravity указывает для Windows PowerShell `irm https://antigravity.google/cli/install.ps1 | iex`; приведённый пользователем `curl ... | bash` относится к macOS/Linux. Установка CLI не равна бесплатному API или бесплатным моделям: в найденной документации описаны установка и аутентификация, но не гарантия бесплатной квоты.

Не подключать его в Compose и не выполнять `curl|bash` вслепую. Сначала скачать скрипт в файл, проверить URL/хэш/подпись и содержимое, затем установить в отдельный контейнер/профиль без доступа к `.env`, MySQL, Redis и media volume. Не передавать ему Threads token, Telegram token или LiteLLM master key. Для SaltGroup допустимый эксперимент — только read-only помощник для анализа уже сохранённых обезличенных метрик; публикация, сообщения, изменение бюджетов и настроек должны оставаться за текущим backend approval gate.

Если нужен бесплатный inference уже сейчас, безопаснее оставить проверенный локальный Ollama/LiteLLM маршрут: в `config.yaml` предусмотрены локальные aliases и fallback-цепочки. Облачные «free» маршруты требуют собственных ключей, имеют изменяющиеся квоты/лимиты и не должны считаться SLA.

## Ограничения

Точный live scope и доступность insights/search зависят от Meta app review, токена и account permissions. Переходы, сохранения, DMs, подтверждённый контакт и hiring outcome отсутствуют в текущих данных/API. Органическое сравнение постов не является A/B-тестом без распределения аудитории. Внешние решения могут показывать функции, которые Threads API не предоставляет этому приложению.

## Визуальная проверка публикации по приложенному скриншоту

Скриншот Threads подтверждает проблемы на опубликованном посте «ВАКАНСІЯ: ВИРОБНИЦТВО КАРТОННИХ КОРОБОК»:

- Заголовок на украинском, но строка `Не вказано в оголошенні` оставлена как незаполненный шаблон. Это выглядит как отсутствие ключевого факта и снижает доверие.
- `Оплата: 23 zł/год PLN` содержит одновременно польское обозначение валюты и код PLN. Для кандидата это выглядит как машинная сборка, а не проверенная ставка.
- `Графік: 06:00–18:00` не сообщает количество дней, сменность, перерывы и фактическую недельную нагрузку. Кандидат не может оценить предложение.
- `Договір: Umowa zlecenie` вставлен без украинского пояснения и без указания, что именно подтверждено источником.
- `Житло: 650 zł/місяць` не уточняет, входит ли это в зарплату, является ли суммой за человека, есть ли депозит и что именно оплачивается. В предыдущих данных проекта встречается формулировка про коммунальные услуги, но в этом посте она потеряна.
- `Напишіть нам, щоб перевірити актуальність місця.` — слабый CTA: нет способа связи, вакансии не присвоены город и конкретное рабочее место, не указаны требования и дата выхода.
- Визуально пост не выделяет город, ставку, график и условия жилья; это ухудшает быстрое сканирование в ленте.
- Метрика на скриншоте: 133 просмотра, 130 зрителей, 0 посещений профиля и 0 подписок. Это не доказывает причинность, но подтверждает отсутствие измеримого перехода от показа к намерению.

### Ошибка сборки данных

Публикация должна быть остановлена до отправки, если обязательное поле имеет значение `Не вказано в оголошенні`, если нет города/источника ставки, если валютная запись не нормализована или если CTA не содержит разрешённого канала связи. Нужен preview с подсветкой незаполненных и изменённых полей и обязательным подтверждением рекрутера.

### Исправление Telegram-парсера — 2026-10-14

Причина потери данных найдена в импортере: украинская метка `Місце роботи` не входила в список location labels; строки `32 зл/год — для студентів` могли попадать в обычную ставку; блок месячного дохода мог ошибочно считаться почасовой ставкой; многострочный `Графік роботи:` без значения в первой строке не разбирался.

Парсер теперь распознаёт эти формы, отделяет обычные и студенческие ставки, пропускает месячные суммы и восстанавливает город из сохранённого описания. Backfill по Telegram-источникам обновил активные записи из исходного `description`: вакансии ID 10/12 получили `Energetyczna 12, 54-530 Krzyżowice` и ставки `25`/`32` зл/год; ID 11 получил `Czechowice-Dziedzice`, `23` и `31,40` zł/год без месячного дохода; ID 6 получил `Wiechlice`, обычные ставки `25,50`/`29` и студенческие `33`/`35` zł/год.

## Supervisor/Guard — 2026-10-13

Добавлен детерминированный Supervisor (`backend/app/supervisor.py`). Он запускается worker-ом периодически и доступен через `GET /api/threads/supervisor` (только наблюдение) и локальный `POST /api/threads/supervisor/scan` (наблюдение плюс allowlist безопасных исправлений).

Supervisor обнаруживает отсутствие Meta scope для mentions, неподдерживаемую настройку `auto_external_comment`, неготовый Threads account, зависшие jobs, просроченные расписания и посты, не проходящие финальную publish-проверку. Автоматические действия ограничены локальным состоянием: остановка auto-post при неготовом account, восстановление stale job, перевод просроченного расписания обратно в APPROVED и quarantine невалидного поста. Публикация, отправка reply, изменение секретов, миграции и редактирование кода из Supervisor запрещены.

Live после пересборки: `GET /api/threads/supervisor` показывает два ручных инцидента — отсутствующий `threads_manage_mentions` и включённый, но нереализованный `auto_external_comment`. Два старых просроченных расписания были автоматически заблокированы как невалидные посты и переведены в `FAILED`; внешний Threads API при этом не вызывался.

После внедрения полный backend-набор: `226 passed`, 4 существующих pytest warning; targeted Supervisor: `5 passed`.

## Продолжение: проверка вакансии без города — 2026-10-14

На приложенном скриншоте подтверждён воспроизводимый дефект: AI-черновик вакансии «Працівник складу одягу» не содержит города, повторяет часть строки про студентов и при этом предлагает отправить текст на проверку. Отдельно в трендовом черновике отображался служебный маркер `[google-news-rss]` и необработанный URL источника.

Исправлено:

- `validate_post_for_publication` теперь блокирует внешний publish для `VACANCY`, если в подтверждённом источнике нет города или ставки, либо город не попал в итоговый текст;
- публикация блокируется при placeholder `Не вказано в оголошенні`, служебных маркерах, дублированной валюте/единице ставки, неподтверждённой ставке и запрещённых Telegram-контактах;
- неполный черновик по-прежнему можно сохранить и отредактировать, но он не может перейти через финальный publish-gate;
- тест идемпотентности публикации переведён на `EDUCATIONAL`, потому что он проверяет очередь и повторы, а не полноту фактов вакансии; отдельный regression-тест проверяет блокировку вакансии без города.

Старые посты и черновики автоматически не удалялись: без явного идентификатора и подтверждения области удаления это небезопасно. Их нужно исправить или архивировать вручную.

Проверка после изменения: полный backend regression — `232 passed`; production frontend ранее успешно собран, Vitest — `14 passed`. Реальная публикация в Threads во время проверки не выполнялась.

Ограничение интеграции остаётся: текущий Meta-токен отвечает `403` на `/mentions`, поэтому полный поток mentions недоступен без scope `threads_manage_mentions` и app review. Доступные replies синхронизируются только в пределах разрешённых API/scopes; комментарии и метрики не выдумываются.

## Корневая причина потери входящих и остановки автогенерации — 2026-10-20

Аудит проведён на живой системе (8 контейнеров, live-режим, аккаунт `_salt_group_` подключён). Найдены и исправлены четыре дефекта, каждый из которых самостоятельно объясняет наблюдаемое поведение.

### 1. Сбор сообщества молча терял ~100% ответов

`LiveThreadsClient.replies()` передавал курсор синхронизации в `GET /{threads-user-id}/threads`. Meta применяет `since` к **времени публикации поста**, а не к времени ответа. Проверено напрямую: без `since` endpoint отдаёт 15 постов (3 с `has_replies=true`), с `since=now-1h` — 0 постов.

Следствие: мониторинг видел только ответы, пришедшие в первый час после публикации поста. Ответ на пост 12.10, пришедший через 81 минуту, терялся навсегда. За 11 дней в базу попали 4 реальных взаимодействия вместо десятков.

Доказательство из API: ветка поста `17928016395184399` содержит 25+ реальных комментариев (`mary__stylish`, `olgasafronova2025`, `ev_pain`, `poteruhinpavel`, `liza_nagornayaa`, `art_dem4enko`, `maksym_prykhodko`, `kirillralen` и другие), из них в `threads_interactions` не было ни одного.

Исправлено: курсор убран из запроса списка постов и применяется к ответам. Добавлено окно пропуска (`reply_scan_interval_minutes`, по умолчанию 30 мин — меньше часа запаса курсора), счётчики потерь в `community_sync_completed` и утилита `scripts/backfill_interactions.py` с режимом `--apply`.

Результат после backfill: взаимодействия 7 → **43**, атрибуция к постам 0 → **36**, сигналы кандидатов 2 → **13**.

### 2. Посты, опубликованные вне системы, не имели атрибуции

Пост `17928016395184399` не существовал в `threads_posts`, поэтому его 25+ ответов не могли быть привязаны ни к чему. Добавлено adopt: посты, подтверждённые как собственные через `GET /{uid}/threads`, заводятся локально с явной пометкой происхождения в `reasoning_summary` и типом содержимого, выведенным из подтверждённых полей.

### 3. Проверка квоты публикаций никогда не срабатывала

Реальный API отдаёт квоту как `{"data": [{...}]}` с объектом `config`, а код ждал список и читал верхний уровень (`threads_client.py`). Итог: `quota_total` не вычислялся, лимит 250 постов в сутки не защищал. Исправлено чтение всех трёх форм ответа.

### 4. `quality_guard_scan` падал каждые 5 минут

`backend/app/quality_guard.py` создавал `ActivityEvent` без поля `category`, а колонка `NOT NULL`. Каждый запуск завершался `IntegrityError`, отчёт не сохранялся, аудит-трейл отсутствовал. **287 упавших job за 24 часа** — больше половины всех отказов в системе. Исправлено точечно и структурно: в модели `category` получил Python-side default `threads`, поэтому забыть поле больше нельзя.

### 5. Контент не генерировался автономно

Три независимые причины:

- **Планировщик просил невозможное.** 6 постов по 500 символов одним вызовом при бюджете 600 токенов. Замер: `count=2` → таймаут 60 с, `count=3` → мгновенный `500 Missing Gemini API key`.
- **Маршрут `free-reasoning` начинался с Gemini без ключа**, а список деплоев перемешивался случайно (`simple-shuffle`). Половина вызовов упиралась в мёртвый маршрут вместо фолбэка на локальную модель.
- **Дубликаты отбрасывались молча.** За 34 плана создано 32 поста, 93 идеи отброшены как дубликаты; последние 10 планов подряд дали `created=0`.

Исправлено:

- планировщик работает батчами по 2 идеи (`PLANNER_BATCH_SIZE`) с повтором до нужного количества; сбой одного батча не отменяет уже полученные идеи;
- промпт урезан (3 вакансии, 5 вопросов, 4 тренда, компактная editor evidence, бюджет фактов 4000 символов) и дополнен списком уже опубликованных начал;
- в `litellm/config.yaml` **оден деплой на алиас**, модель/api-base/ключ задаются переменными окружения; keyless-облачные маршруты удалены, случайного перемешивания больше нет; таймауты расширены под 4B-модель;
- повторяющийся ракурс **заменяется** детерминированным углом из подтверждённых фактов вакансии (`backend/app/editorial_angles.py`) вместо пустого слота;
- дедупликация ограничена окном в 21 день; семейство шаблона применяется только к fallback-контенту;
- метка источника `[google-news-rss]` убрана из текста тренда — она была служебным маркером и блокировалась publish-gate.

Результат: ручной запуск `POST /api/threads/content-plan?count=3` → `created=3, skipped=0` за ~2 минуты; все три черновика автоматически поставлены в расписание (16:00, 18:30, 06:00) без участия оператора.

### 7. План создавал шесть одинаковых постов за раз — 2026-10-21

После исправления выше ежедневный план заработал, но за один запуск создал **6 постов, и все шесть были про одно и то же**: ставка для студентов + вычет жилья из зарплаты, различались только формулировками. Дедупликация сравнивает текст буквально, поэтому смысловые дубли проходили.

Проверка детектора тем на тех же шести постах: у всех `primary_subject = HOUSING`.

Исправлено:

- `backend/app/content_subjects.py` — каждый текст сводится к набору тем (`HOUSING`, `PAY`, `SCHEDULE`, `CONTRACT`, `CITY`, `TRANSPORT`, `REQUIREMENTS`) и к одной основной теме. Детектор читает только маркеры условий и ничего не домысливает.
- Внутри одного плана две публикации не могут иметь одну основную тему. Повтор заменяется детерминированным ракурсом, у которого своя тема; ракурсы `RATE`, `SCHEDULE`, `HOUSING`, `CONTRACT`, `CITY`, `TRANSPORT`, `REQUIREMENTS` дают семь разных тем.
- Планировщик получает список уже закрытых тем и уже опубликованных начал — как подсказку; жёсткое правило остаётся в worker.
- В интерфейсе заголовок больше не печатается, если текст публикации начинается с него же: заголовок и есть первая фраза текста, раньше она показывалась дважды.

Результат на живых данных: `POST /api/threads/content-plan?count=6` → `created=4, skipped=5, substituted=3`. Созданные публикации — разные темы: HOUSING (ИИ), PAY, SCHEDULE, CITY, все автоматически в расписании. Пять лишних черновиков из предыдущего запуска (105–108 и 104) переведены в ARCHIVED, чтобы не опубликоваться; пост 103 оставлен.

Проверка после внедрения: полный backend regression — `268 passed`; frontend Vitest — `17 passed`; production frontend build — успешно.

## Агенты: кто реально работает и почему контент не шёл — 2026-10-21

Страница «ИИ-агенты» показывала пять включённых помощников, но по факту ни один не писал контент сам, а ручной запуск задерживал публикации. Разбор по живым данным.

### Что агенты делают на самом деле

| Агент | Модель | Было | Стало | Что даёт |
| --- | --- | --- | --- | --- |
| ANALYST | нет | 84 мс | 83 мс | детерминированный отчёт по метрикам, ничего не предлагает |
| SCOUT | нет | 663 мс | 526 мс | сбор публичных тем; без `threads_keyword_search` даёт 0 |
| COMMUNITY | на новые комментарии | 1 231 мс | 1 660 мс | **доставка входящих** — единственный, кто приносит реальные данные |
| STRATEGIST | да | **200 046 мс** | **14 008 мс** | один новый ракурс контента |
| WRITER | да | **179 088 мс** | **67 600 мс** | один черновик |

Замеры после исправлений — все пять завершились успешно, без «Резервного шаблона после ошибки ИИ».

### Причина 1: Hermes отнимал модель у контент-пайплайна

STRATEGIST шёл через Hermes — агентный runtime поверх той же локальной модели. Его системный промпт — **13 012 токенов**, а окно локальной модели 4096–8192. Каждый вызов упирался в таймаут (200 с), а Hermes **повторял запрос с backoff**: цикл 180 с + 90 с на фолбэк-цепочке, заново и заново. Пока Hermes крутился, модель была занята его префиллом, и планировщик контента упирался в собственный таймаут.

Тот же вопрос стратега через обычный маршрут LiteLLM отрабатывает за 38 с. Исправлено: стратег спрашивает настроенный маршрут напрямую, Hermes оставлен опцией (`HERMES_FOR_STRATEGIST`, по умолчанию `false`), а сервис Hermes переведён в профиль `hermes` и по умолчанию не стартует.

### Причина 2: ручной запуск агента задерживал публикацию

Обработчик заданий один и обрабатывает их последовательно. Агент занимал его на 130–200 с, а задания публикации стояли в той же очереди — кнопка «Запустить» могла сдвинуть эфир.

Исправлено: у заданий появился приоритет (публикация → сбор метрик → синхронизация → контент → агенты), а медленные модельные задания (`run_agent`, `content_plan`) вынесены в отдельный сервис `worker-agents`. Ручной запуск агента больше не может задержать публикацию.

### Причина 3: таймаут маршрута обрывал рабочий вызов

`free-default` отдавал таймаут на 90 с, а планировщику нужно 90–130 с. Маршруты перенастроены: `free-default` и `free-reasoning` — 180 с, `free-fast` — 120 с, клиентский `ai_timeout_seconds` — 200 с.

### Причина 4: страница вводила в заблуждение

«Агенты работают через настроенные маршруты LiteLLM» — но ANALYST, SCOUT и COMMUNITY модель не вызывают. «Анализирует результаты и предлагает улучшения» — не предлагает, а печатает расчёт. Описания переписаны: у каждого агента указано, использует ли он модель; для неиспользующих маршрут показан как «не используется». Заголовок страницы теперь прямо говорит, что ежедневный контент создаёт планировщик, а не эти кнопки.

### Что осталось честным ограничением

Три из пяти агентов дублируют то, что планировщик уже делает сам (COMMUNITY — каждые 5 минут, SCOUT — каждые 6 часов, WRITER — подмножество ежедневного плана). Их кнопки полезны как «сделай сейчас», но автономной работы они не добавляют. Реально новый артефакт создаёт только STRATEGIST, и именно он был сломан.

Проверка: полный backend regression — `272 passed`; frontend Vitest — `17 passed`.

## Апгрейд: ежедневный ракурс и отчёт о разрешениях — 2026-10-21

### 1. Ракурсы стратега не доходили до планировщика

Проверка данных показала: накоплено 5 тем с `source='strategist'`, все в статусе `PLANNED`, и **ни одна не была прочитана**. Планировщик брал только `threads-keyword-search` и `google-news-rss`. То есть единственный агент, создающий новый артефакт, производил его в никуда — а ежедневный запуск только добавил бы копий.

Исправлено:

- планировщик читает и ракурсы стратега (`source` включён в выборку, окно 14 дней);
- ракурс стратега запускается **ежедневно** (`auto_strategy_angle`, ключ `agent-strategy:{дата}:auto`); он выполняется отдельным воркером агентов и не задерживает публикацию;
- одинаковые и близкие по смыслу ракурсы отбрасываются (пересечение значимых слов ≥ 60 %): модель формулировала одну мысль разными словами, и список тем забивался перефразами;
- 20 накопленных дублей «Explain the real conditions for…» и перефразов в статусе `PLANNED` переведены в `ARCHIVED`, осталось 6 уникальных ракурсов.

### 2. Отчёт о разрешениях Meta

Отсутствующие scope в Meta не дают явной ошибки: часть функций молча не работает. Добавлен `backend/app/capabilities.py` и `GET /api/threads/capabilities` — что выдано, чего не хватает, что остаётся невидимым и где это запросить. Тот же блок показан на странице «Аккаунт» с пошаговой инструкцией оператору.

Текущее состояние аккаунта: выдано `threads_basic` и `threads_content_publish`; не хватает `threads_read_replies`, `threads_manage_replies`, `threads_manage_insights`, `threads_manage_mentions`, `threads_keyword_search`. Отчёт прямо перечисляет последствия: упоминания в чужих постах не видны, ответить в чужом треде нельзя, публичные обсуждения не ищутся, метрики охвата неполны.

`docs/meta-scopes-request.md` — готовый к подаче документ: что запрашивать, обоснование по каждому scope, что указать в форме App Review, как проверить после выдачи и что изменится в системе.

### 3. Путь выдачи разрешений был закрыт на полпути

Разрешения читались **только при подключении**: ни обновление токена, ни
проверка соединения их не перечитывают. Оператор выдаёт scope в Meta,
нажимает «Проверить подключение» — и отчёт остаётся старым, показывает
прежнее состояние и создаёт ложное впечатление, что ничего не изменилось.

Исправлено: `POST /api/threads/account/test` перечитывает выданные
разрешения через `debug_token` и сохраняет их, а изменение попадает в
журнал активности как `threads_account_permissions_changed` с перечнем
добавленных и отозванных разрешений. Кнопка «Проверить подключение» на
странице «Аккаунт» обновляет отчёт о разрешениях.

### 4. Всплеск упоминаний не должен задерживать публикации

С разрешением `threads_manage_mentions` синхронизация начнёт получать
упоминания. Разбор каждого нового комментария делал **один вызов модели** с
общим таймаутом 200 с: тридцать упоминаний — это минуты блокировки
воркера, а публикации стоят в той же очереди.

Исправлено: разбор комментария получил отдельный короткий таймаут (45 с), а
число модельных разборов за цикл ограничено пятью (`COMMENT_MODEL_ANALYSES_PER_CYCLE`).
Остальные комментарии разбираются детерминированно — тема, тональность и
риск считаются без модели, а в кампании фиксируется, что разбор был
детерминированным.

### 5. Прочее

- `HERMES_ENABLED=false` по умолчанию: отключённый необязательный сервис больше не деградирует общий статус здоровья.

Проверка: полный backend regression — `280 passed`; frontend Vitest — `17 passed`.

## Подключение OmniRoute как основной модели — 2026-10-21

Локальная 4B-модель была узким местом: 90–130 с на один вызов планировщика,
таймауты на грани, заметно более слабый украинский. Подключён локальный
шлюз OmniRoute (OpenAI-совместимый `/v1`, 12 провайдеров), локальная модель
осталась резервом.

### Что изменилось в маршрутизации

| Алиас | Модель | Назначение |
| --- | --- | --- |
| `free-fast` | `antigravity/gemini-3.1-flash-lite` | разбор комментариев, быстрые правки |
| `free-default` | `antigravity/gemini-3-flash` | написание постов |
| `free-reasoning` | `antigravity/gemini-3.8-flash-high` | планирование, стратегии, анализ |
| `local` | `ollama_chat/qwen3:4b-instruct` | **резерв**: конец цепочки фолбэков |

Локальная модель — последнее звено каждой цепочки:
`free-default → [free-reasoning, local]`. Если шлюз, его ключ или его
провайдеры исчерпаны, контент-пайплайн продолжает работать на собственной
модели машины. Таймауты подобраны под это: облачные маршруты 45–60 с, локальный
180 с, запрос шлюза 260 с.

### Почему модели заданы явно

- **`auto/*`-маршруты OmniRoute не используются.** Они выбирают модель на
  каждый запрос, и язык ответа следует за моделью: один и тот же украинский
  промпт дал **польский** ответ от `auto/best-reasoning` и **английский** от
  `auto/best-free`. Publish-gate отверг бы оба, то есть непредсказуемый язык
  — это остановка выпуска контента.
- **Уровни reasoning не используются.** `gemini-3.8-flash-low` потратил 565
  из 696 выходных токенов на размышление и не вернул текста вовсе.
- **Варианты Claude отвечали пустым телом** с `finish_reason=length`.

### Замеры

Украинский рекрутинговый промпт: `gemini-3.1-flash-lite` 1.6 с,
`gemini-3-flash` 1.7 с, `gemini-3.8-flash-high` 2.8 с — корректный украинский,
без токенов на размышление. Тот же промпт на локальной 4B-модели: 90–130 с.
**Ежедневный контент-план: 176 с → 13 с.** Качество текста выше: «Від чого
насправді залежить ставка… звичайний працівник 25,50 zł/год netto, а з
правами UDT вже 29 zł/год netto» — верные факты, украинские формы, вопрос в
начале.

### Приватность

Вопросы аудитории — это реальные комментарии кандидатов, и они теперь уходят
в сторонние провайдеры. Перед отправкой в модель упоминания маскируются
(`_mask_handles`): содержание вопроса планировщику нужно, а имя человека —
нет. Факт согласия и текст комментария в модель не уходят.

### Проверка

Полный backend regression — `287 passed`; frontend Vitest — `17 passed`;
резервный маршрут `local` проверен отдельно (3.3 с на коротком промпте);
ежедневный план перезапущен вживую — 13 с, 2 публикации созданы и
автоматически поставлены в расписание.

## Воронка «сигнал → контакт → кандидат» — 2026-10-21

Аудит зафиксировал: «Атрибуция пока заканчивается на сигнале. Модели связывают interaction → post и signal → candidate, но нет сущностей подтверждённого контакта, consent, канала контакта, recruiter outcome или hiring result. Интерфейс кнопкой „Создать кандидата“ превращает сигнал в карточку, что не является подтверждением квалификации».

Состояние до изменений: 14 сигналов, 0 кандидатов, 0 подтверждённых контактов. Показатель «сигналы кандидатов» стоял в одной строке с прочими KPI, то есть неотвеченный вопрос выглядел как результат.

### Правила

- **Сигнал не является кандидатом.** Запись кандидата создаётся только с подтверждённым каналом связи: `POST /api/threads/candidate-signals/{id}/convert` требует `channel` и `contact_value`, без них — `422`. Прежний контракт (одна кнопка без данных) больше не работает.
- **Этапы воронки**: `NEW → CONTACTED → QUALIFIED → HIRED`, плюс `REJECTED`. Переходы заданы таблицей `ALLOWED_STAGE_TRANSITIONS`; недопустимый переход — `409`. Для найма и отказа обязательно указание причины.
- **Каждый переход фиксируется**: новая таблица `threads_candidate_stage_events` хранит `from_stage → to_stage`, кто решил и почему. История доступна через `GET /api/candidates/{id}/history`.
- **Согласие фиксируется отдельно** от факта контакта: `consent_given` и `consent_at`. Контакт подтверждён, но согласие не получено — это разные факты, и они видны по отдельности.
- **Дашборд показывает подтверждённую воронку**, а не сырые сигналы: «сигналы в очереди → контакт подтверждён → квалифицированы → наняты». Счётчик сигналов убран из общей строки KPI, где он стоял рядом с показателями публикаций.

### Миграция и интерфейс

`0012_candidate_funnel`: в `candidates` добавлены `channel`, `contact_value`, `confirmed_by`, `confirmed_at`, `consent_given`, `consent_at`; создана `threads_candidate_stage_events`.

Страница «Кандидаты» переписана: строка KPI воронки, диалог подтверждения контакта с выбором канала и фиксацией согласия, таблица кандидатов с текущим этапом и переходом на следующий.

### Проверка

Полный backend regression — `287 passed` (7 новых тестов на воронку); frontend Vitest — `17 passed`; production frontend build — успешно; миграция `0012_candidate_funnel` применена.

## Autonomy Policy Engine — 2026-10-21

Режим автономии сделан не переключателем, а серверным движком политики внутри существующего Control Plane. Второй очереди, второго планировщика и параллельной системы разрешений не появилось.

### Модель

Одна строка `threads_autonomy_policy` — единственный источник истины: режим, версия, лимиты, аварийная остановка, список тем для автоответов, список платформ, требования к проверкам. Старые флаги `auto_post` / `auto_reply` / `auto_external_comment` стали **производными** от режима и больше не читаются как источник разрешения. При первом запуске режим выводится из старых флагов один раз: `auto_post=true` → `SEMI_AUTO`.

### Матрица

| Действие | Manual | Semi-auto | Auto |
| --- | --- | --- | --- |
| Сбор и классификация сигналов | авто | авто | авто |
| Анализ аудитории и вакансий | авто | авто | авто |
| Генерация контента | авто | авто | авто |
| Планирование публикаций | одобрение | авто после одобрения | авто |
| Публикация | одобрение | авто по утверждённому плану | авто после QA |
| Ответы на комментарии | одобрение | авто для разрешённых тем | авто в рамках политики |
| Жалобы, конфликты, персональные данные | человек | человек | человек |

### Реализованные технические условия

1. **Единый источник истины** — см. выше; противоречащие настройки невозможны.
2. **Проверка непосредственно перед действием.** Решение принимается в воркере перед вызовом Threads, а не при постановке в очередь. Проверено вживую: публикация поста 110, ждавшая в очереди, после переключения в Manual была остановлена в момент выполнения — пост вернулся в `APPROVED`, расписание снято, причина записана.
3. **Аварийная остановка** — `emergency_stop` блокирует публикации и ответы, не останавливая сбор и аналитику.
4. **Полный аудит** — `threads_policy_decisions` хранит действие, решение, причину, режим, версию политики, актора и время. Смена режима пишется в `ActivityEvent` (кто, когда, из какого режима в какой, почему).
5. **Ограничения автономности** — лимиты публикаций в сутки и в час, ответов в сутки; превышение даёт `DENY` с причиной.
6. **Fail closed** — ошибка проверки политики даёт `DENY`, а не разрешение. Покрыто тестом.

Отдельно: политика управляет **автоматическими** действиями. Явное действие человека (кнопка «Опубликовать») проходит во всех режимах — это решение оператора, а не автономия.

### Auto заблокирован структурно

`AUTO` нельзя включить, пока не реализованы проверка актуальности вакансий и модельная проверка текста: движок возвращает `409` со списком причин. Это соответствует требованию «Auto нельзя случайно включить в обход QA, актуальности данных или платформенных разрешений».

### Operator Panel

Раздел «Автономность системы» в настройках: переключатель режима с описанием, блокеры Auto, аварийная остановка, таблица матрицы, лимиты и журнал решений политики.

### Проверка

Полный backend regression — `312 passed` (17 новых тестов политики: режимы, emergency stop, fail closed, гонка исполнения, аудит, лимиты, блокировка Auto); frontend Vitest — `17 passed`; миграция `0014_autonomy_policy` применена; остановка уже поставленной публикации проверена на живой системе.

## Vacancy Freshness и Model QA — 2026-10-21

Две проверки, без которых `AUTO` включать нельзя. Реализованы, и `AUTO` разблокирован структурно: `auto_available` возвращает `true` (аккаунт имеет `threads_content_publish`), при этом режим остаётся `SEMI_AUTO` — включать его оператор.

### Vacancy Freshness

Свежесть — это **состояние**, а не вывод из даты. У вакансии появились `source_confirmed_at`, `source_drifted_at`, `source_drift_note`.

- `UNVERIFIED` — источник ни разу не подтверждался человеком; условия сверить не с чем. Так у всех 13 активных вакансий на момент внедрения.
- `FRESH` — источник подтверждён не позже 14 дней назад.
- `STALE` — подтверждение старше 14 дней: сигнал проверить, а не доказательство, что вакансия закрыта.
- `DRIFTED` — источник изменился после публикации. Это сильнее «устарело»: опубликованные условия больше не совпадают с источником.

Дрейт ловится автоматически: Telegram-импортёр получает `edited_channel_post` и сравнивает извлечённые факты с сохранёнными. При расхождении вакансия помечается как `DRIFTED`, а посты, процитировавшие старые цифры, перечисляются в событии `vacancy_source_drifted`.

Ручное подтверждение источника (`POST /vacancies/{id}/verify-source`) теперь записывает `source_confirmed_at` и снимает дрейт. Состояние возвращается в ответе и в инспекции вакансии.

### Model QA

`backend/app/model_qa.py` — смысловая проверка текста перед публикацией: язык, поддержка каждого утверждения подтверждёнными условиями, честность обещаний и голос рекрутера. Ответ — маленький перечислимый список находок, чтобы его нельзя было «разговорить».

Проверка **односторонняя**: она может заблокировать публикацию, но никогда не снимает блокировку детерминированного гейта. Сломанный или бессмысленный ответ модели — это «не пройдено», а не «пройдено по умолчанию».

Результат хранится на посте (`model_qa_passed`, `model_qa_notes`, `model_qa_at`) и считается непосредственно перед публикацией — в режиме `AUTO`. Повторная попытка не повторяет вызов модели.

### Что нашлось на живых данных

Проверка на реальных постах сразу дала находки:

- посты 129–131 — **пройдены** (написанные украинской, без шаблонных следов и необоснованных обещаний);
- пост 132 — **заблокирован**: в нём упомянуто производство картонных коробок, которого нет в подтверждённых условиях вакансии №17. До появления QA такой текст ушёл бы в эфир.

Попутно исправлено ложное срабатывание: посты, не связанные с вакансией, попадали на проверку без единого подтверждённого условия, и QA справедливо считал все утверждения неподтверждёнными. Теперь планировщик связывает пост с вакансией, условия которой он реально цитирует (`_match_vacancy`), а проверка без фактов оценивает только язык и голос.

### Проверка

Полный backend regression — `324 passed` (11 новых тестов на свежесть и QA: неподтверждённый источник, устаревший, дрейт, повторное подтверждение, успешная и неуспешная вычитка, сломанная вычитка, негодный ответ, сбой без названной причины, блокировка публикации в Auto после неуспешной вычитки); миграция `0015_freshness_and_model_qa` применена.
