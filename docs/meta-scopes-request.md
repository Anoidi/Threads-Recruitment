# Запрос дополнительных разрешений Threads API

> Уточнение аудита 26.10.2026: у действующего токена `@_salt_group_` подтверждены
> пять прав: basic, content_publish, manage_replies, read_replies, manage_insights
> (с префиксом `threads_`). Старые статусы ниже не являются актуальной
> диагностикой. Meta возвращает их в `data.scopes`; чтение этого поля исправлено.
> Отсутствие scope у токена не доказывает необходимость App Review: сначала
> проверить выбранные права, роль тестировщика и заново выдать токен.
> App Review проверяется отдельно для доступа пользователей вне ролей приложения.
> Упоминания и поиск у проверенного токена отсутствуют. Подробности и ограничения:
> `THREADS_INTEGRATION_AUDIT.md` в корне проекта.

Документ для подачи в Meta Developer Portal. Без этих разрешений система
видит только тех кандидатов, которые ответили под нашими постами, и не может
отвечать в чужих обсуждениях.

## Куда подавать

**Meta Developer Portal → Ваше приложение → Threads API → Permissions and
Features → Request advanced access**

Приложение: `Threads Recruitment Manager`
App ID: указан в `.env` как `THREADS_APP_ID`.

## Какие разрешения запрашивать и зачем

| Разрешение | Статус | Зачем продукту | Что не работает без него |
| --- | --- | --- | --- |
| `threads_basic` | есть | базовый доступ к профилю, квоте и проверке подключения | аккаунт не подключается |
| `threads_content_publish` | есть | публикация постов и ответов | нельзя опубликовать ничего |
| `threads_read_replies` | **запросить** | чтение дерева ответов под нашими постами | мы не знаем, какие вопросы нам задают под нашими публикациями |
| `threads_manage_replies` | **запросить** | отвечать в обсуждениях, где нас спросили | видим вопрос, но ответить в чужом треде не можем |
| `threads_manage_insights` | **запросить** | просмотры, ответы, репосты и цитаты по своим постам | метрики неполны, сравнение форматов ненадёжно |
| `threads_manage_mentions` | **запросить** | публичные посты, где упомянут наш аккаунт | не видим спрос, который возникает вне наших постов |
| `threads_keyword_search` | **запросить** | поиск чужих публичных обсуждений по ключевым словам | разведчик идёт только по новостям, а не по живому спросу |

## Почему это нужно именно рекрутинговому аккаунту

Аккаунт публикует вакансии и вакансии для работников в Польше. Кандидаты
задают вопросы о ставке, жилье, графике и договоре — как правило, в ответах
под нашими постами, в чужих обсуждениях о работе и в публичных упоминаниях.

Без `threads_manage_mentions` и `threads_keyword_search` система не видит ни
одного обращения, которое возникло вне наших публикаций. Из-за этого
профиль аудитории остаётся односторонним, а контент-план отвечает только на
вопросы, которые нам уже принесли под нашими же постами.

## Что нужно указать в обосновании

1. **Использование API** — автоматическая публикация вакансий и ответов на
   вопросы кандидатов от имени рекрутингового аккаунта, чтение ответов под
   собственными публикациями, сбор статистики собственных публикаций.
2. **Тип аккаунта** — организация, публикующая вакансии от своего имени.
3. **Видео** — не используется. API применяется только к текстовым публикациям
   и ответам.
4. **Поведение пользователя** — доступ запрашивается для конкретного
   рекрутингового аккаунта, и все действия проходят через подтверждение
   оператора: ни одно внешнее действие не выполняется автоматически.
5. **Обращение** — указать контакт владельца аккаунта и дать ссылку на
   демонстрацию работы системы.

## Как проверить после выдачи

Обновление long-lived токена **не добавляет новых разрешений**: Meta выдаёт
scope только при новом запросе пользователя. Поэтому после одобрения нужно
выпустить новый токен с полным набором разрешений.

```powershell
# 1. Переподключить аккаунт: страница «Аккаунт» → «Заменить токен Meta».
#    В генераторе токенов Meta отметить все семь разрешений:
#      threads_basic, threads_content_publish, threads_read_replies,
#      threads_manage_replies, threads_manage_insights,
#      threads_manage_mentions, threads_keyword_search

# 2. Проверить, что Meta действительно выдала новые разрешения
Invoke-RestMethod http://localhost:8000/api/threads/capabilities

# 3. Нажать «Проверить подключение» на странице «Аккаунт».
#    Приложение перечитает выданные разрешения через debug_token
#    и обновит отчёт.

# 4. Убедиться, что упоминания больше не дают 403
docker compose logs --tail 50 worker | Select-String "optional_sync_unavailable"

# 5. Проверить, что аудитория начала пополняться
Invoke-RestMethod http://localhost:8000/api/threads/audience
```

Ожидаемое изменение в отчёте о разрешениях: `missing` становится пустым, а
`granted` содержит все семь имён. В журнале активности появляется событие
`threads_account_permissions_changed` с перечнем добавленных разрешений.

## Что происходит в системе, когда разрешения появляются

- `threads_manage_mentions` — начинают собираться упоминания аккаунта в чужих
  публикациях, и профиль аудитории перестаёт быть односторонним. Разбор
  новых комментариев ограничен пятью вызовами модели за цикл, поэтому
  всплеск упоминаний не задерживает публикации.
- `threads_manage_replies` — появляется возможность отвечать в чужих
  тредах; сейчас в интерфейсе доступна только отправка ответа в свой тред.
- `threads_read_replies` — полное дерево ответов под своими постами.
- `threads_manage_insights` — полные метрики по охвату; сравнение форматов
  перестаёт быть неполным.
- `threads_keyword_search` — разведчик начинает находить публичные
  обсуждения, и покрытие трендов в аналитике переключается с
  `unavailable` на `available`.

## Ограничения, которые Meta не снимет

- Разрешения выдаются на конкретное приложение и на конкретный аккаунт.
- Лимит публикаций Threads Tester — 250 постов в сутки. Для рабочего аккаунта
  нужен собственный профиль, а не тестовый аккаунт Meta.
- `threads_manage_insights` не даёт метрики чужих публикаций: доступны только
  собственные.
